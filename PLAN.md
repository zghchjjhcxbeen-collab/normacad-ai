# NormaCAD AI — план MVP

> Документ построен «с нуля от идеи». Исходный handoff друга использован только как фундамент. План прошёл многоагентное исследование (ЕСКД, парсинг DXF/DWG, PDF/OCR, Claude vision, архитектура, рынок, стек) и адверсариальную критику. Критические правки рецензента уже учтены в приоритетах — это главная ценность документа.

---

## 0. Идея и ценность

**NormaCAD AI** — B2B-сервис **предварительного** ИИ-нормоконтроля машиностроительных и конструкторских чертежей по ГОСТ/ЕСКД. Инженер или нормоконтролёр загружает чертёж в любом формате (PDF, DXF, DWG, PNG, JPG) → сервис прогоняет его через гибридный конвейер (детерминированный парсинг вектора + Claude vision для растра и семантики) → возвращает отчёт со списком замечаний, где каждое привязано к пункту ГОСТ и к месту на чертеже. Ценность: **сократить число возвратов документации** от нормоконтроля к конструктору, отсеяв грубые формальные ошибки до того, как лист попадёт к живому нормоконтролёру.

---

## 1. Позиционирование (фундамент, влияет на всё)

- Мы — **предварительный фильтр, а не замена нормоконтролёра** (ЕСКД формально добровольного применения, ответственность за выпуск КД остаётся на человеке — ср. ГОСТ 2.111). Это снимает главную репутационную и юридическую мину.
- В отчёте — градация **«ошибка / предупреждение / рекомендация»**, а не безапелляционное «нарушение».
- Главный конкурентный моат против «голого ChatGPT-сервиса»: **измеримые факты (высоты, толщины, расстояния, формат листа) всегда из детерминированного парсера, а не из LLM.** LLM не имеет права придумывать числа.
- Главное преимущество против встроенных модулей нормоконтроля (Нормоконтроль для AutoCAD, КОМПАС, СПДС): мы **формат-агностичны** — работаем с PDF, сканами и чужими форматами, а не только внутри одного CAD.
- В отчёте всегда присутствует явный блок **«требует ручной проверки нормоконтролёра»** для того, что мы сознательно не автоматизируем.

## 1a. Реальность после уточнений с владельцем (сужает и оздоровляет скоуп)

Три ответа владельца меняют приоритеты:

1. **Форматы — все сразу, без доминирующего.** Универсальное покрытие любых форматов достигается только vision-путём (рендер → картинка → модель), т.к. что угодно сводится к изображению. Значит, vision — ранний универсальный слой, а не опция «на потом».
2. **Среди клиентов есть режимные/секретные предприятия.** Отправлять их КД в зарубежное облако Claude нельзя. Это прямо противоречит п.1: облачный vision как универсальный движок недопустим для части рынка. → **ИИ-ядро проектируется offline-способным с первого дня; vision-движок — подключаемый бэкенд** (облачный Claude для гражданки/демо ⟷ локальная open-weights VLM для изолированного контура ⟷ выключен). Для секретного сегмента вероятна **on-prem поставка** (клиент разворачивает Docker Compose у себя), а не наш SaaS — подтвердить (раздел 11).
3. **Реальных чертежей и эксперта-нормоконтролёра сейчас нет.** Корпус появится только при выходе на предприятия; их штатный НК и станет первым проверяющим ИИ. → Калибровать на реальных данных сейчас нечем.

**Вывод — MVP сужается до честно достижимого ядра:**
- **Высокоточные детерминированные проверки** (формат 2.301, масштаб 2.302, высоты шрифта 2.304, наличие/заполненность штампа 2.104) на форматах, парсимых **офлайн** (DXF, вектор-PDF). Эти правила объективны — проверяются по тексту ГОСТ без корпуса и без эксперта, достаточно нескольких тестовых файлов.
- Это и есть **то, что показываем на первой демонстрации** — только «железобетонные» проверки, без шатких геометрии/семантики, чтобы штатный НК предприятия не поймал ИИ на ошибке в первую же минуту.
- **Первая демонстрация = первая реальная валидация.** Механизм обратной связи от НК (отметить ложное / добавить пропущенное) строим рано — это единственный источник истины до появления корпуса.
- Vision и «тяжёлые» форматы (сканы, картинки, DWG-fallback) — подключаемый слой поверх ядра: для несекретного сегмента через облако, для секретного — через локальную VLM (Phase 2).

## 2. Цели и НЕ-цели MVP

**Цели:**
- Сквозной путь работает: загрузка → постановка задачи → асинхронная обработка → отчёт с привязкой замечаний к месту.
- Детерминированное ядро даёт **почти безошибочные** проверки (precision ≥ 0.95) на узком, проверенном наборе правил.
- Честная коммуникация скоупа: что проверено автоматически, что — на совести человека.
- **Каждое замечание содержит рекомендацию «как исправить»** (для детерминированных правил — конкретную, вплоть до ближайшего допустимого значения: формат/масштаб/высота/графа).
- **На сайте есть ИИ-чат со справочником по ГОСТ** (RAG над базой ГОСТов): вопрос клиента → поиск стандарта в `index.json` → ответ с цитатой пункта. Бэкенд подключаемый (облачный Claude для гражданки / локальная модель для секретного контура), как и vision; тексты ГОСТ не передаются целиком (копирайт) — только короткие выдержки.

**НЕ-цели MVP (сознательно отложено):**
- Не претендуем на полноту нормоконтроля (достаточность простановки размеров, замкнутость размерных цепей, достаточность видов, соответствие шероховатости функции поверхности — НЕ обещаем).
- Не биллинг, не мультиорганизационный B2B-тенантинг, не интеграции с PLM/CAD по API.
- Не дообучение моделей (но локальная open-weights VLM как подключаемый бэкенд — задел, не цель MVP).
- Не on-prem поставка и не локальная VLM в самом MVP — это Phase 2 для секретного сегмента; MVP-демо идёт через облачный/гражданский контур.
- Не глубокая проверка всех форматов сразу: приём принимает все форматы, но **высокая точность гарантируется только для офлайн-парсимых** (DXF, вектор-PDF); сканы/картинки/DWG в MVP — best-effort через vision.
- Не «замена нормоконтролёра».

## 3. Итоговый стек

| Слой | Выбор | Обоснование |
|---|---|---|
| **Бэкенд** | FastAPI + Pydantic + SQLAlchemy (async) | Весь тяжёлый стек (ezdxf, рендер PDF, геометрия, Anthropic SDK) — Python-native. Один язык на API и воркере = переиспользование парсеров и моделей. Менять язык для 1–2 человек = раскол стека. |
| **Фронт** | Jinja2 + htmx + Alpine.js (SSR, без SPA) | Дашборд MVP — это формы загрузки, поллинг статуса, списки, страница отчёта. htmx закрывает поллинг (`hx-trigger="every 3s"`) и фрагменты; Alpine — локальную интерактивность. Нет npm-билда, CORS, дублирования типов. SSR идеально ложится на cookie-сессии. |
| **Просмотрщик чертежа** | изолированный островок (SVG-оверлей bbox / PDF.js) внутри Alpine | Единственное место с заметным клиентским JS — подсветка замечаний по координатам. Не требует перехода на SPA. |
| **БД** | PostgreSQL сразу (не SQLite) | Конкурентная запись: API создаёт задачу, воркер обновляет статус/результат. SQLite сериализует запись → `SQLITE_BUSY`. Postgres даёт MVCC, JSONB (отчёт, bbox, counts), нормальные миграции (Alembic). Цена входа на Docker Compose ≈ ноль. |
| **Очередь/воркер** | ARQ + Redis | Обработка чертежа — десятки секунд. BackgroundTasks не дают статусов/ретраев и гибнут с web-процессом. ARQ async-native под FastAPI, встроены ретраи/таймауты/статусы. Redis заодно = хранилище сессий + кэш дедупа + pub/sub прогресса. |
| **Хранилище** | локальная ФС за абстракцией `Storage` → S3/MinIO позже | Путь `{user_id}/{sha256}/{name}` даёт естественную дедупликацию. Бинарники не в БД. |
| **Аутентификация** | серверные сессии в cookie (HttpOnly + Secure + SameSite=Lax), сессии в Redis, **без JWT** | Согласовано с SSR. Простая ревокация (logout = удаление серверной сессии). Обязательна CSRF-защита на мутациях. JWT/API-key — в роадмап под программный доступ. |
| **Парсинг DXF** | ezdxf | Читает DXF напрямую: слои, TEXT/MTEXT (+height), DIMENSION (`get_measurement`), INSERT/ATTRIB, геометрия, `$INSUNITS`. |
| **DWG → DXF** | ⚠️ конвертер под вопросом (spike + лицензия) | ezdxf **не читает DWG**. Бесплатный ODA File Converter **запрещён для SaaS**. Альтернативы (Aspose.CAD — платно; LibreDWG — нестабилен на сложных DWG) требуют проверки. **DWG в MVP — за гейтом, см. Этап −1.** |
| **PDF/растр** | pypdfium2 (рендер) + pdfplumber (парсинг) + PaddleOCR (ru) | ⚠️ PyMuPDF под **AGPL-3.0** → для SaaS нужна коммерческая лицензия Artifex. По умолчанию берём связку pypdfium2 (Apache/BSD) + pdfplumber (MIT), решение зафиксировать до коммерческого релиза. |
| **vision-LLM (подключаемый бэкенд)** | облачный Claude (гражданка/демо) ⟷ локальная open-weights VLM (изолированный контур) ⟷ выкл. | Универсальный слой для растра и любых форматов. Для секретных клиентов облако недопустимо → бэкенд абстрагирован за интерфейсом `VisionBackend` с 1-го дня. Модель/стоимость/железо — spike (Этап −1). Числа в Finding всегда из парсера, не из vision. |
| **Деплой** | облачный SaaS: один VPS (РФ) + Docker Compose (`api`, `worker`, `postgres`, `redis`, `caddy`); **тот же образ — для on-prem** | SaaS для гражданки/демо. Секретный сегмент разворачивает Docker Compose в своём изолированном контуре (Phase 2). Бэкап = pg_dump + том файлов. K8s преждевременен. |

## 4. Архитектура: гибридный ИИ-пайплайн

Воркер — это **роутер-стратегия по MIME-типу**. Архитектурный инвариант: **каждое замечание на любой стадии несёт локатор** (handle примитива в векторе / `bbox + page` на растре). Это требование к структуре парсера, а не пост-обработка.

```
STAGE 0  ВАЛИДАЦИЯ ВХОДА
  magic bytes (allowlist pdf/dxf/dwg/png/jpg) · лимит размера (потоково) ·
  SHA-256 · пиксельный лимит (защита от «бомб») · [опц.] антивирус
        │ routing по формату
        ├──────────┬───────────────┬──────────────┬─────────────────┐
        ▼          ▼               ▼              ▼                 ▼
      DWG         DXF             PDF          PNG/JPG         крупный A1/A0
        │ ODA      │      classify born-digital     │            (любой)
        │ →DXF     │      vs скан vs HYBRID         │               │
        │ (spike!) │          │        │            │               ▼
        ▼          ▼          ▼        ▼            ▼          ТАЙЛИНГ листа
  ┌─────────────────────────┐ │  ┌──────────────────────┐    на тайлы+overlap,
  │ 1A ВЕКТОРНЫЙ ПАРСИНГ     │ │  │ 1B РАСТРОВЫЙ ТРАКТ    │    bbox→глоб.коорд.
  │ (ezdxf)                 │ │  │ • рендер 300–400 DPI  │
  │ • $INSUNITS → мм        │ │  │ • deskew, бинаризация │
  │ • слои, TEXT/MTEXT+h,   │ │  │ • детект рамки/штампа │
  │   DIMENSION, INSERT,    │ │  │ • OCR по кропам зон   │
  │   геометрия примитивов  │ │  │   (PaddleOCR ru)      │
  │ • рамка/штамп: блок →   │ │  │ • crop полей штампа   │
  │   fallback bbox.extents │ │  │   по сетке 2.104      │
  └───────────┬─────────────┘ │  └───────────┬──────────┘
              │   вектор-PDF → │ путь 1A      │
              ▼                ▼              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ STAGE 2  ДЕТЕРМИНИРОВАННЫЕ ПРОВЕРКИ (движок правил)            │
  │ применяются к вектору; на растре — только надёжное (наличие)  │
  │ каждое правило → Finding(rule_code, severity, locator,       │
  │ source=deterministic); константы ЕСКД = версионируемый конфиг │
  └───────────────────────────┬─────────────────────────────────┘
                              │ эскалация: растр / семантика / low-confidence
                              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ STAGE 3  CLAUDE VISION (адресно, по кропам зон, высокий DPI)  │
  │ семантика: достаточность видов 2.305, смысл/порядок ТТ 2.316, │
  │ непротиворечивость 2.109, смысловая валидация граф штампа     │
  │ → Finding(source=vision, confidence). Числа НЕ отсюда.       │
  └───────────────────────────┬─────────────────────────────────┘
                              ▼
  STAGE 4  НОРМАЛИЗАЦИЯ → единый Finding + дедуп пересекающихся
                              ▼
  STAGE 5  СБОРКА Report: summary, counts_by_severity, ruleset_version,
           блок «требует ручной проверки», status=done
```

**Узлы, требующие особого внимания (по итогам критики):**
- **Нормализация единиц** (`$INSUNITS`): при `0`/unitless или ненативном масштабе модели **геометрические проверки в мм НЕ запускаются** — выдаются в блок «уточните единицы», а не считают заведомо ложные нарушения. Фактический масштаб определяется сверкой `get_measurement` с измеренной геометрией.
- **Классификатор PDF**: три класса — `born-digital`, `скан`, `hybrid/uncertain`. Скан с наложенным OCR-слоем (невидимый текст / GlyphlessFont) не считать born-digital. Если вектор-тракт нашёл подозрительно мало примитивов — **деградировать в растровый**, а не отдавать пустой отчёт.
- **Тайлинг и vision**: правила, требующие видеть лист целиком (2.305 достаточность видов), **несовместимы с тайлингом** — либо целый лист на пониженном DPI, либо вне MVP.

## 5. Каталог проверок ЕСКД

Severity: `critical / major / minor / info`. Приоритет: **P0** (вертикальный срез) → **P1** → **P2**.
**Важно (правка критики):** проверки, требующие реконструкции топологии чертежа (что есть «контур», что есть «ось»), помечены 🔬 — они НЕ считаются гарантированно детерминируемыми до technical spike (Этап −1). По его итогам они либо сужаются, либо уходят в assistive/vision с пометкой low-confidence.

### Детерминированные (код) — ядро ценности

| Правило | ГОСТ | Что проверяем | Приоритет | Форматы |
|---|---|---|---|---|
| Формат листа | 2.301-68 | габариты рамки/MediaBox ∈ {A4…A0} с допуском | **P0** | DXF, вектор-PDF |
| Масштаб из ряда | 2.302-68 | строка масштаба (графа 6) ∈ whitelist (regexp) | **P0** | DXF, вектор-PDF |
| Наличие/заполненность штампа | 2.104-2006 | детект таблицы в правом нижнем углу; непустота обязательных граф (наименование, обозначение, масштаб, подписи разработчика+НК, даты) | **P0** | DXF, вектор-PDF |
| Высоты шрифта из ряда | 2.304-81 | height TEXT/MTEXT → мм ∈ {2,5; 3,5; 5; 7; 10; 14; 20; 28; 40}, ≥ 3,5 для основных | **P0** | DXF, вектор-PDF |
| Толщина/типы линий | 2.303-68 | основная s=0,5…1,4 мм; тонкие s/3…s/2; одинаковость в масштабе | **P1** | DXF, вектор-PDF |
| 🔬 Геометрия размеров | 2.307-2011 | ≥7 мм между размерными, ≥10 мм до контура, выход выносных 1–5 мм, знаки Ø/R/□ | **P1 (gated)** | DXF, вектор-PDF |
| 🔬 Геометрия знака шероховатости | 2.309-73 | пропорции знака, наличие Ra/Rz, общий знак в правом верхнем углу | **P1 (gated)** | DXF, вектор-PDF |
| 🔬 Буквенные обозначения сечений | 2.305-2008 | парность «А-А» линия↔изображение, наличие стрелок | **P2 (gated)** | DXF, вектор-PDF |
| Согласованность сносок «*» | 2.109-73 | «*» в поле ↔ «*» в техтребованиях | **P2** | DXF, вектор-PDF |

### Через LLM (Claude vision) — семантика и растр

| Правило | ГОСТ | Что проверяем | Приоритет | Форматы |
|---|---|---|---|---|
| OCR + наличие элементов на растре | 2.104/2.301/2.302 | чтение граф штампа, грубое наличие рамки/штампа/масштаба | **P0 (для растра)** | PNG, JPG, скан-PDF |
| Смысловая валидация граф штампа | 2.104-2006 | корректность наименования, согласованность обозначения | **P1** | все |
| Достаточность/выбор видов | 2.305-2008 | правильность главного вида, достаточность изображений (целый лист!) | **P2** | все |
| Осмысленность и порядок ТТ | 2.316 | типовой порядок (допуски→покрытия→термообработка), противоречия с полем | **P2** | все |

### Вне MVP — блок «требует ручной проверки нормоконтролёра»

Полнота и замкнутость размерных цепей, достаточность простановки размеров (2.307); достаточность/минимальность изображений (2.305); соответствие шероховатости/допусков функции поверхности; корректность децимального номера по классификатору. **Не обещаем** — честная коммуникация скоупа.

> Каждый Finding ссылается на **номер и пункт актуальной редакции** ГОСТ из версионируемого конфига. Юридическая корректность формулировки/пункта — подтверждается действующим экспертом ЕСКД (см. Этап 3, gate).

## 6. Модель данных

```
User 1───N Drawing 1───N CheckJob 1───1 Report
                                    └───N Finding
```

- **User**: id, email (unique), password_hash, org_id (nullable, задел под B2B), created_at.
- **Drawing**: id, user_id, original_name (санитизировано), stored_path (`{user}/{sha256}/{name}`), mime (по magic bytes), size, **sha256 (index, дедуп)**, format_class (`vector_dxf`/`vector_dwg`/`vector_pdf`/`raster`), page_count, created_at.
- **CheckJob**: id, drawing_id, user_id, status (`queued`/`running`/`done`/`failed`), attempts, error_text, **ruleset_version**, units_assumed (bool), queued_at/started_at/finished_at. Идемпотентный ключ дедупа: `job_id = f"check:{drawing_id}:{ruleset_version}"`.
- **Finding**: id, job_id, rule_code, rule_clause, rule_title, severity (enum), message, page, **bbox jsonb `[x,y,w,h]`** (или handle), source (`deterministic`/`vision`), confidence (nullable), status (`open`/`accepted`/`dismissed` — отметка нормоконтролёра).
- **Report**: id, job_id (1:1), summary, total_findings, counts_by_severity (jsonb), manual_check_items (jsonb), ruleset_version, generated_at, format.

> Перед записью findings воркер чистит прежние findings этого job — повторный прогон идемпотентен.

## 8. Дорожная карта по этапам

Порядок продиктован зависимостями. **Этап −1 — блокирующее предусловие всего проекта** (главная правка критики: без эталонного корпуса и spike-ов вся инженерия калибруется на синтетике и переписывается в конце).

Оценки разделены на **И** (инженерия, оцениваема) и **R&D** (неопределённый исход — оценивается timeboxed-spike с гейтом go/no-go, а не фиксированными ЧД). Единица — человеко-дни (ЧД).

---

### Этап −1. Бутстрап тест-данных + spikes + бизнес-трек 🚧
**Реальность:** реального корпуса и эксперта-НК сейчас нет (ответы владельца). Поэтому этап раздваивается на инженерный (можно начать сразу) и бизнесовый (ответственность владельца).

**Инженерный трек:**
- Собрать **бутстрап-набор** из доступного: примеры из текста ГОСТ/учебников, публичные/обезличенные DXF, и **синтетические чертежи**, сделанные специально под каждое правило (заведомо чистые и заведомо нарушающие).
- **Spike геометрии** (на доступных DXF): доля ассоциативных `DIMENSION` vs взорванных в LINE/TEXT; есть ли слоевая семантика (контур/ось/размеры на разных слоях). → решение по 🔬-правилам.
- **Spike DWG**: надёжность LibreDWG/Aspose-конвертации + потери объектов (DIMENSION, блоки, шероховатость).
- **Spike vision-бэкенда**: сравнить облачный Claude (гражданка) и локальную open-weights VLM (изолированный контур) — качество, требования к GPU, латентность, стоимость на A1-лист.

**Бизнес-трек (параллельно, владелец):**
- Найти **пилотное предприятие**, готовое дать 30–50 реальных чертежей с замечаниями НК и подключить штатного нормоконтролёра как валидатора. **Это блокер для перехода к фаззи-проверкам (геометрия/семантика) и к измерению реального recall** — но НЕ блокер для офлайн-ядра P0.

**Дедливераблы:** бутстрап-набор в репозитории; отчёты по 3 spike с go/no-go; список кандидатов в пилот.
**Acceptance (проверяемо):**
- Бутстрап-набор покрывает каждое P0-правило минимум 1 чистым и 1 нарушающим примером.
- По каждому spike — письменное go/no-go и его влияние на скоуп.
- В коде и отчётах явно зафиксировано: **все метрики до пилота — предварительные** (на бутстрапе/синтетике), не репрезентативны для реальных чертежей.

> ⚠️ Без пилотного предприятия проект строится частично «вслепую»: высокоточное офлайн-ядро (формат/масштаб/шрифт/штамп) сделать и проверить можно, а фаззи-проверки и реальный recall — нет. Это осознанный риск, не дефект плана.

**Оценка:** И, 6–10 ЧД (инженерный трек) + бизнес-трек по календарю владельца.

---

### Этап 0. Вертикальный срез (DXF, end-to-end)
**Цель:** система работает насквозь на одном формате (DXF) и 3–4 проверках P0.
**Задачи:** скелет FastAPI + PostgreSQL(+Alembic) + Jinja2/htmx; auth на cookie-сессиях; `POST /uploads` (только DXF); ARQ-воркер со статусами `queued→running→done/failed`; парсер ezdxf (`$INSUNITS`→мм, TEXT/MTEXT, INSERT, рамка); движок правил с версионируемым конфигом + 4 правила P0 (2.301, 2.302, 2.304, 2.104-наличие); Finding с локатором; сборка Report; страница отчёта + **просмотрщик DXF→SVG с подсветкой bbox**; htmx-поллинг.
**Дедливерабл:** загрузил DXF → job_id → поллинг → отчёт с замечаниями (правило + пункт ГОСТ + место).
**Acceptance:** на бутстрап-наборе DXF каждое из 4 правил: **precision ≥ 0.95, recall ≥ 0.85** (предварительно, до пилота); bbox каждого Finding совпадает с эталоном по **IoU ≥ 0.5**; «чистый» эталонный чертёж даёт 0 ложных critical/major.
**Оценка:** И, 10–15 ЧД.

---

### Этап 1. Аутентификация и hardening загрузки
**Цель:** довести auth и приём файлов до прод-минимума.
**Задачи:** регистрация/логин/логаут; сессии в Redis; CSRF на мутациях; потоковая валидация размера и magic bytes; SHA-256 и дедуп по hash+ruleset; rate-limit на `/auth/*` и `/uploads`; санитизация имён.
**Acceptance:** попытка загрузить не-allowlist MIME / превысить лимит / переслать без CSRF — отклоняется с понятной ошибкой; повторная загрузка идентичного файла переиспользует Drawing; нет паролей/session_id в логах.
**Оценка:** И, 5–8 ЧД.

---

### Этап 2. Устойчивость очереди
**Цель:** воркер не теряет и не дублирует задачи.
**Задачи:** job_timeout; ретраи **только транзиентных** ошибок (не парсинг-ошибок); идемпотентность по job_id; статус `failed` с error_text; `POST /jobs/{id}/retry`.
**Acceptance:** убитый посреди обработки воркер → задача восстанавливается без дубля findings; нетранзиентная ошибка парсинга → `failed` без бесконечных ретраев; повторный enqueue того же job_id не плодит работу.
**Оценка:** И, 4–6 ЧД.

---

### Этап 3. Расширение детерминированных проверок (по итогам spike)
**Цель:** добавить только те правила, что подтверждены spike геометрии.
**Задачи:** 2.303 (типы/толщины линий по слоям/lineweight); 🔬 2.307/2.309 — **в объёме, разрешённом spike** (если топология нереконструируема — понизить до assistive low-confidence или в vision-тракт); **верификация каждого правила и его пункта ГОСТ действующим экспертом ЕСКД** (gate, фиксируется в метаданных ruleset: дата, редакция, кем подтверждено).
**Acceptance:** каждое релизнутое правило: precision ≥ 0.95 на корпусе; правило без подтверждения эксперта **не релизится**; при `units_assumed` геометрия в мм не запускается, а уходит в «требует ручной проверки».
**Оценка:** И+R&D, 12–25 ЧД (вилка зависит от исхода spike).

---

### Этап 4. Векторный PDF
**Цель:** принимать born-digital PDF тем же ядром правил.
**Задачи:** классификатор PDF (`born-digital`/`скан`/`hybrid`); извлечение текста/геометрии (pypdfium2 + pdfplumber); таблица штампа; маршрутизация born-digital → тракт 1A; fallback в растр при подозрительно малом числе примитивов.
**Acceptance:** на корпусе PDF классификатор: точность отнесения к классу ≥ 0.9; born-digital PDF даёт те же замечания, что эквивалентный DXF (расхождение ≤ заранее согласованной дельты); ни один скан с OCR-слоем не уходит ошибочно в вектор-тракт.
**Оценка:** И, 8–12 ЧД.

---

### Этап 5. Растровый тракт + OCR (с гейтом качества)
**Цель:** обрабатывать PNG/JPG/скан-PDF.
**Задачи:** рендер/нормализация; deskew, бинаризация; детект рамки и штампа; OCR русского (PaddleOCR); crop полей штампа по сетке 2.104; **числовой гейт пригодности скана** (эффективный DPI, доля OCR-боксов с confidence ≥ порога, успех детекта рамки).
**Acceptance:** на корпусе сканов: OCR обязательных граф штампа — точность по символам ≥ заранее согласованного числа на «годных» сканах; скан ниже гейта качества → отчёт с единственным выводом «качество недостаточно», **без** геометрических findings; нет потока ложных critical на плохих сканах.
**Оценка:** R&D, 14–22 ЧД (OCR штампа на реальных сканах — итеративный).

---

### Этап 6. Claude vision (опциональный, gated по правилам и приватности)
**Цель:** семантические проверки и растровая эскалация.
**Задачи:** интеграция Anthropic SDK; промпт под каждое правило + few-shot; structured output (tool use / JSON-схема) с локатором; тайлинг крупных листов с пересчётом bbox; дедуп пересекающихся findings; калибровка confidence; **бюджет токенов/стоимости на лист**; human-in-the-loop валидация выборки находок нормоконтролёром перед включением **каждого** vision-правила; **ветка «vision отключён»** для изолированного контура (приватность).
**Acceptance:** для каждого vision-правила — числовые пороги на корпусе (напр. 2.316 порядок ТТ: recall ≥ 0.7 при precision ≥ 0.6 на N листах), иначе правило не релизится → backlog; правила, требующие целого листа (2.305), не обрабатываются тайлами; стоимость ≤ согласованного порога руб./лист; при отключённом vision продукт остаётся работоспособным на детерминированном ядре.
**Оценка:** R&D, 12–18 ЧД + итерации на качество.

---

### Этап 7. DWG (за лицензионным гейтом)
**Цель:** принимать DWG, если spike и лицензия позволили.
**Задачи:** конвертер DWG→DXF в sandbox с timeout; graceful degrade «загрузите DXF/PDF» при сбое; учёт потерь объектов из spike.
**Acceptance:** доля успешных конвертаций корпуса DWG ≥ согласованного порога; потери критичных объектов (DIMENSION/штамп) не приводят к ложным findings (при потере — деградация, не выдумывание); лицензия конвертера юридически чиста для SaaS.
**Оценка:** И, 6–10 ЧД (только при go из Этапа −1).

---

### Этап 8. Отчёт, экспорт в формат бюро, история
**Цель:** встроить вывод в реальный документооборот нормоконтроля.
**Задачи:** главный вывод — **размеченный чертёж: ошибки подсвечены прямо на листе, по клику — пункт ГОСТ** (основной просмотрщик уже в Этапе 0); история проверок; профиль/настройки. **Опционально, по запросу конкретного бюро** — экспорт в редактируемую xlsx/doc-ведомость замечаний (зона / пункт ГОСТ / замечание / severity). Excel НЕ обязателен: это лишь мостик в бумажный документооборот, а не способ работы ИИ — основной канал вывода — сам чертёж.
**Acceptance:** экспортированную ведомость нормоконтролёр целевого бюро признаёт пригодной для возврата конструктору без перенабора; на плотном листе триаж позволяет за минуту отсеять ложные срабатывания.
**Оценка:** И, 8–12 ЧД.

---

### Этап 9. Пилот приёмки с нормоконтролёром
**Цель:** измерить **реальный** precision/recall, а не синтетический.
**Задачи:** 2–4 недели параллельной работы на реальном потоке бюро (ИИ + ручной НК на одних чертежах); кнопка «добавить пропущенное ИИ замечание» (`POST /manual-finding`) как источник false-negative; экран сверки «отчёт ИИ vs финальное заключение НК»; обучение порогов на dismiss-сигнале.
**Acceptance:** на реальном потоке: precision детерминированного ядра ≥ 0.95, доля пропущенных ИИ формальных замечаний (false-negative) измерена и ниже согласованного порога; владелец и НК подтверждают, что сервис сокращает возвраты.
**Оценка:** календарный пилот 2–4 недели + 5–8 ЧД на инструменты сверки.

## 9. Метрики качества (сквозные)

- **Детерминированные правила:** precision ≥ 0.95, recall ≥ 0.85 на правило (почти безошибочны — иначе подрывают доверие профессионала).
- **Vision-правила:** пороги ниже и **индивидуальны на правило**; confidence калибруется, не берётся сырым.
- **bbox-локатор:** IoU ≥ 0.5 с эталоном.
- **Скан-гейт:** числовой порог пригодности до запуска OCR.
- **До пилота все метрики предварительны** (на бутстрап-наборе/синтетике) и не репрезентативны для реальных чертежей. Реальные precision/recall измеряются только на **пилоте** (Этап 9) на чертежах предприятия. Это явно коммуницируется и в отчётах, и владельцу.

| **Итого MVP** | **~95–150 ЧД** + буфер 30–40% на R&D-этапы + календарная зависимость от корпуса/эксперта/пилота. Реалистичная вилка до «MVP с подтверждённым на реальных данных качеством»: **150–220 ЧД.** |

> Эта вилка сознательно выше «оптимистичных» оценок: стадии с геометрией, OCR и vision — это R&D с неопределённым исходом, а не предсказуемая инженерия.

## Что дальше (следующий шаг работы)

Офлайн-ядро P0 НЕ блокировано отсутствием корпуса — начинаем с **Этапа 0 (вертикальный срез)**: каркас FastAPI + PostgreSQL + ARQ + ezdxf + 4 железобетонные проверки (формат/масштаб/шрифт/штамп) + просмотрщик с подсветкой. Это то, что несём на первую демонстрацию. Параллельно: инженерный трек **Этапа −1** (бутстрап-набор + 3 spike) и бизнес-трек владельца (**поиск пилотного предприятия** — без него фаззи-проверки и реальный recall не сделать). Vision подключаем как отдельный бэкенд только после офлайн-ядра.
